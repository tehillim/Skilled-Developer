# Claude를 유능한 개발자로 만들기 위해 필요한 것

> English version: [What It Takes to Make Claude a Skilled Developer](en/making-claude-a-skilled-developer.md)

AI 코딩 에이전트(Claude)는 그 자체로 코드를 잘 작성하지만, **실제로 유능한 개발자처럼 일하게 만드는 것은 주변 환경과 협업 방식**입니다. 유능한 신입 개발자가 합류했을 때 온보딩이 필요하듯, Claude에게도 같은 것이 필요합니다.

## 1. 컨텍스트

Claude는 매 세션마다 프로젝트를 처음 봅니다. 사람 개발자가 수개월에 걸쳐 쌓는 암묵지를 문서로 명시해 줘야 합니다.

### CLAUDE.md 작성 (가장 중요)

저장소 루트의 `CLAUDE.md`는 Claude가 세션 시작 시 자동으로 읽는 온보딩 문서입니다. 다음을 담으세요.

- **프로젝트 개요**: 무엇을 하는 프로젝트인지 한두 문단
- **자주 쓰는 명령어**: 빌드, 테스트, 린트, 실행 방법 (예: `npm test`, `make build`)
- **디렉터리 구조**: 어디에 무엇이 있는지
- **코딩 컨벤션**: 네이밍 규칙, 에러 처리 방식, 사용하는/피하는 패턴
- **주의사항**: 건드리면 안 되는 파일, 알려진 함정, 레거시 영역

`/init` 명령으로 초안을 자동 생성한 뒤 다듬는 것이 빠릅니다.

### 그 외 도움이 되는 문서

- **아키텍처 문서**: 모듈 간 의존 관계, 데이터 흐름, 왜 이런 구조를 택했는지(ADR)
- **용어집**: 도메인 용어와 코드 내 명칭의 대응 관계
- **API/스키마 문서**: 외부 계약이 코드만으로 파악하기 어려울 때

> 원칙: "새로 온 시니어 개발자가 문서만 읽고 첫 PR을 올릴 수 있는가?" 그렇다면 Claude도 잘 일할 수 있습니다.

### 예시: 최소한의 CLAUDE.md

완벽한 문서를 목표로 하면 시작이 늦어집니다. 아래 정도의 분량이면 첫 버전으로 충분하고, 부족한 부분은 이후 세션에서 드러날 때마다 채워 가면 됩니다(6장 참고).

```markdown
# MyApp

주문/결제를 처리하는 커머스 백엔드. Node.js 20 + TypeScript + PostgreSQL.

## 명령어

- 개발 서버: `npm run dev`
- 테스트: `npm test` / 타입 검사: `npm run typecheck`
- 환경 설정: `./scripts/setup.sh` 한 번이면 끝

## 구조

- `src/api/` — HTTP 핸들러 (얇게 유지, 비즈니스 로직 금지)
- `src/services/` — 비즈니스 로직
- `src/db/` — 스키마와 마이그레이션

## 컨벤션

- 에러는 throw하지 말고 `Result` 타입으로 반환
- 금액은 항상 정수 KRW — `Money` 타입만 사용

## 주의사항

- `src/legacy/`는 수정 금지 (교체 예정, 테스트 없음)
```

항목마다 한 줄씩이라도 "무엇을 실행할지, 어디를 볼지, 무엇을 피할지"가 명시되어 있으면, 세션 초반의 탐색 시간과 잘못된 추측이 크게 줄어듭니다.

### 예시: 모호한 설명 vs 구체적인 설명

같은 항목이라도 얼마나 구체적으로 적었는지에 따라 Claude가 실제로 활용할 수 있는지가 갈립니다.

| 모호한 설명 | 구체적인 설명 |
|---|---|
| "결제 모듈은 복잡하니 조심하세요" | "`src/payments/`는 외부 PG사 API와 직접 연동됩니다. 금액은 항상 원(KRW) 정수 단위로 다루고, 소수점 반올림 오차로 실제 결제 사고가 난 적이 있으니 `Money` 타입만 사용하세요." |
| "테스트는 꼼꼼히 작성해주세요" | "새 API 엔드포인트는 성공 케이스 1개 + 실패 케이스 2개 이상을 `tests/api/`에 작성하고, `npm run test:api`로 통과를 확인하세요." |

"복잡하다", "꼼꼼히" 같은 표현은 사람에게도 모호합니다. 구체적인 파일 경로, 이유, 확인 방법이 있어야 Claude가 그대로 실천할 수 있습니다.

### 예시: 용어집

도메인 용어와 코드 명칭이 다르면 Claude는 엉뚱한 곳을 찾거나 새 이름을 만들어 냅니다. 짧은 표라도 대응 관계를 적어 두면 코드 탐색과 네이밍이 일관돼집니다.

```markdown
## 용어집

| 도메인 용어 | 코드 명칭 | 비고 |
|---|---|---|
| 가맹점 | `Merchant` | UI에는 "스토어"로 표기하지만 코드에서는 Merchant만 사용 |
| 정산 | `Settlement` | `Payout`은 레거시 명칭 — 신규 코드에서 사용 금지 |
| 주문 확정 | `OrderConfirmation` | 결제 완료(`PaymentCompleted`)와는 다른 개념 |
```

"정산 로직 고쳐줘"라는 요청을 받았을 때 용어집이 있으면 Claude는 레거시 `Payout`이 아니라 `Settlement`를 찾아가고, 새 코드에도 팀이 쓰는 이름을 그대로 사용합니다.

### 예시: ADR (아키텍처 결정 기록)

코드에는 "무엇"만 남고 "왜"는 남지 않습니다. 왜 그 구조를 택했는지가 기록되어 있지 않으면, Claude는 과거에 검토 후 기각된 방식을 "개선"이라며 다시 제안할 수 있습니다. 결정 하나당 짧은 파일 하나면 충분합니다.

```markdown
# ADR-007: 주문 이벤트는 메시지 큐 대신 outbox 테이블로 발행

## 상태
승인됨 (2025-03)

## 맥락
주문 생성과 이벤트 발행이 서로 다른 시스템에 걸쳐 있어,
큐 장애 시 "주문은 생겼는데 이벤트는 유실"되는 문제가 있었다.

## 결정
이벤트를 DB 트랜잭션 안에서 outbox 테이블에 함께 쓰고,
별도 릴레이가 큐로 전달한다.

## 결과
- 주문과 이벤트의 원자성 보장. 대신 발행이 수 초 지연될 수 있음
- `src/orders/`에서 큐 클라이언트를 직접 호출하는 코드는 금지
```

이 파일이 `docs/adr/`에 있으면, Claude는 "이벤트를 큐로 바로 쏘면 더 단순하겠는데요"라는 제안 대신 outbox 패턴을 따르고, 위반 코드를 발견하면 지적할 수 있습니다.

### 예시: 모노레포에는 디렉터리별 CLAUDE.md

여러 패키지가 한 저장소에 있는 모노레포에서 루트 CLAUDE.md 하나에 모든 규칙을 담으면, 문서는 길어지는데 정작 각 패키지 작업에 필요한 규칙은 찾기 어려워집니다. CLAUDE.md는 하위 디렉터리에도 둘 수 있고, Claude는 그 디렉터리의 파일을 다룰 때 해당 문서를 함께 참고합니다.

```text
repo/
├── CLAUDE.md              ← 공통: 전체 구조, 공통 명령어, 커밋 규칙
├── apps/web/CLAUDE.md     ← 웹 전용: Next.js 컨벤션, 컴포넌트 규칙
├── apps/api/CLAUDE.md     ← API 전용: 에러 응답 형식, DB 접근 규칙
└── packages/shared/CLAUDE.md ← 변경 시 양쪽 앱 테스트 필수 등 주의사항
```

루트에는 어디서나 적용되는 것만 남기고, 특정 패키지에만 해당하는 규칙은 그 패키지의 CLAUDE.md로 내려보내세요. `apps/api/`만 고치는 세션이 웹 프론트엔드 컨벤션까지 읽을 필요가 없어지고, 규칙이 적용 범위 가까이에 있으니 코드가 바뀔 때 문서도 같은 PR에서 갱신되기 쉬워집니다(6장 참고).

## 2. 검증 가능한 개발 환경

Claude는 코드를 **실행하고 확인할 수 있을 때** 훨씬 유능해집니다. 추측으로 작성한 코드와 실행해서 검증한 코드는 품질 차이가 큽니다.

- **한 명령으로 빌드/테스트가 돌아가야 합니다.** `npm test`, `pytest`, `make check`처럼 표준적인 진입점을 제공하세요.
- **의존성 설치가 자동화**되어 있어야 합니다. lockfile을 커밋하고, 셋업 스크립트(`scripts/setup.sh` 등)를 두세요.
- **환경 변수와 시크릿**은 `.env.example`로 어떤 값이 필요한지 알려 주세요. 실제 값 없이도 테스트가 돌아가면 이상적입니다.
- **원격/웹 세션이라면** SessionStart 훅으로 의존성 설치를 자동화할 수 있습니다.

### 예시: 셋업 스크립트

의존성 설치, `.env` 준비, 헬스체크를 한 스크립트로 묶어 두면 Claude가 매번 "무엇부터 실행해야 하는지" 추측하지 않아도 됩니다. `CLAUDE.md`에는 "환경 설정은 `./scripts/setup.sh` 하나로 끝납니다"라고만 적어 두면 충분합니다.

```bash
#!/usr/bin/env bash
# scripts/setup.sh
set -euo pipefail

echo "Installing dependencies..."
npm ci

if [ ! -f .env ]; then
  echo "Creating .env from .env.example"
  cp .env.example .env
fi

echo "Running healthcheck..."
npm run typecheck
```

### 예시: .env.example

변수 이름만 나열하지 말고, 각 값이 무엇인지·어디서 얻는지·비워 두면 어떻게 되는지를 주석으로 남기세요. Claude는 실제 시크릿 없이도 어떤 설정이 필요한지 파악하고, 실패가 환경 문제인지 코드 문제인지 구분할 수 있습니다.

```bash
# .env.example — 실제 값은 커밋하지 말고 .env에만 넣으세요

# 로컬 개발용 DB. scripts/setup.sh가 도커로 띄워 줍니다
DATABASE_URL=postgres://localhost:5432/myapp_dev

# 결제 PG 샌드박스 키 — 팀 위키 "시크릿" 페이지에서 발급
PAYMENT_API_KEY=

# 비워 두면 알림 대신 콘솔 출력으로 대체됩니다 (테스트는 없이도 통과)
SLACK_WEBHOOK_URL=
```

"이 키가 없으면 어떤 테스트가 실패하는지"까지 적혀 있으면, Claude는 시크릿이 없는 환경에서도 실패 원인을 코드 탓으로 오판하지 않고 정확히 보고할 수 있습니다.

### 예시: 외부 의존성은 도커로 띄우기

테스트가 DB나 Redis를 필요로 하는데 실행 환경에 없다면, Claude는 테스트를 건너뛰거나 목(mock)으로 대체한 채 진행하게 됩니다. `docker-compose.yml`로 외부 의존성을 정의해 두면 어떤 환경에서도 같은 명령으로 실제 테스트가 돌아갑니다.

```yaml
# docker-compose.yml — 테스트에 필요한 외부 의존성 정의
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: myapp_dev
    ports:
      - "5432:5432"
  redis:
    image: redis:7
    ports:
      - "6379:6379"
```

CLAUDE.md에는 "테스트 전에 `docker compose up -d` 실행" 한 줄이면 충분하고, 셋업 스크립트(위 예시)에 포함시키면 그 한 줄도 필요 없습니다. 의존성 버전까지 파일에 고정되므로 "내 로컬에서는 됐는데" 류의 환경 차이도 사라집니다.

### 예시: 시드 데이터로 검증 결과를 예측 가능하게 만들기

DB는 떴는데(위 예시) 데이터가 비어 있거나 매번 다르다면, Claude는 코드를 실행해 놓고도 "결과가 맞는지"를 판단할 수 없습니다. 항상 같은 상태를 만들어 주는 시드 명령을 제공하고, 그 데이터에 무엇이 들어 있는지를 문서에 남기세요.

```markdown
## 테스트 데이터

`npm run db:seed` — 로컬 DB를 항상 같은 상태로 초기화합니다.

- 사용자 3명: alice(관리자), bob, carol
- 주문 5건: PAID 3건, CANCELLED 2건 (모두 bob 소유)
- 상품 2종: 재고 있음 1, 품절 1
```

이제 "취소된 주문만 조회하는 API를 만들어줘"라는 작업에서 Claude는 API를 호출해 **정확히 2건**이 나오는지까지 확인하고 끝낼 수 있습니다. 시드 내용이 문서에 없으면 실행 결과가 나와도 그것이 정답인지 알 수 없으니, "실행 가능한 환경"의 마지막 조각은 예측 가능한 데이터입니다.

### 예시: 런타임 버전도 파일로 고정하기

lockfile은 라이브러리 버전을 고정하지만, 그 위에서 도는 Node나 Python 자체의 버전은 고정하지 않습니다. 로컬은 Node 20인데 CI는 18이라면, Claude는 자신이 재현할 수 없는 실패를 놓고 코드를 의심하게 됩니다. 런타임 버전도 파일로 저장소에 남기세요.

```bash
# .nvmrc — nvm과 CI의 setup-node가 함께 읽습니다
20.11.1
```

```json
// package.json — 버전이 안 맞으면 설치 단계에서 바로 실패하도록
{
  "engines": { "node": ">=20 <21" }
}
```

버전이 파일로 존재하면 세 곳이 맞춰집니다: 사람의 로컬(`nvm use`), CI(`actions/setup-node`의 `node-version-file`), 그리고 Claude — 환경이 이상할 때 이 파일과 실제 버전(`node --version`)을 비교해 "코드 문제가 아니라 런타임 버전 차이"라고 정확히 진단할 수 있습니다. 파이썬이라면 `.python-version`, 여러 도구를 쓴다면 mise의 `.tool-versions` 하나로 같은 효과를 냅니다. 위의 도커 예시가 외부 의존성의 버전을 고정한다면, 이 예시는 실행 환경 자체의 버전을 고정합니다.

## 3. 빠른 피드백 루프

유능한 개발자는 자기 코드가 틀렸는지 스스로 알아챕니다. Claude에게 그 감각을 주는 것이 자동화된 검증입니다.

| 도구 | 역할 |
|---|---|
| **테스트 스위트** | 동작 보장. 커버리지가 높을수록 Claude가 과감하게 리팩터링할 수 있음 |
| **타입 시스템** | TypeScript, mypy 등. 잘못된 코드를 실행 전에 잡아 줌 |
| **린터/포매터** | ESLint, ruff, prettier 등. 스타일 논쟁을 기계에 위임 |
| **CI** | PR마다 자동 검증. Claude가 CI 실패를 보고 스스로 고칠 수 있음 |

포인트는 **Claude가 이 도구들을 직접 실행할 수 있어야 한다**는 것입니다. 테스트가 있어도 실행법이 문서에 없으면 무용지물입니다.

### 예시: CI 워크플로우

PR마다 테스트와 린트가 자동으로 돌아가면, Claude가 로컬에서 놓친 문제를 CI가 잡아 주고 Claude는 그 결과를 보고 스스로 수정할 수 있습니다.

```yaml
# .github/workflows/ci.yml
name: CI
on: [pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm run lint
      - run: npm test
```

핵심은 **로컬에서 쓰는 것과 동일한 명령(`npm run lint`, `npm test`)을 CI에서도 그대로 실행**하는 것입니다. 명령이 다르면 "로컬에서는 됐는데 CI에서만 실패"하는 상황이 반복됩니다.

### 예시: 전체 테스트가 느릴 때 부분 실행 명령 제공하기

전체 테스트가 10분 걸린다면 Claude는 수정→확인 사이클마다 10분을 기다리거나, 확인을 건너뛰고 추측으로 진행하게 됩니다. 파일 하나, 케이스 하나만 빠르게 돌리는 방법을 CLAUDE.md에 적어 두세요.

```markdown
## 테스트 실행

- 전체 스위트: `npm test` (약 10분 — 커밋 직전에만)
- 파일 하나: `npx jest tests/api/orders.test.ts`
- 케이스 하나: `npx jest -t "주문 취소"`
- 타입 검사만: `npm run typecheck` (수 초 — 수정 직후 1차 확인용)
```

피드백 루프가 수 초 단위로 줄면 Claude는 수정할 때마다 검증하면서 진행합니다. 검증 주기가 짧을수록 잘못된 방향으로 멀리 가기 전에 되돌아올 수 있습니다.

### 예시: 컨벤션을 린트 규칙으로 강제하기

CLAUDE.md에 적힌 규칙은 Claude가 읽고 따르는 약속이지만, 린트 규칙으로 표현할 수 있는 규칙은 기계가 검증하는 규칙이 됩니다. 예를 들어 "새 코드에서 `src/legacy/` import 금지"는 ESLint로 강제할 수 있습니다.

```json
// .eslintrc.json
{
  "rules": {
    "no-restricted-imports": ["error", {
      "patterns": [{
        "group": ["**/legacy/*"],
        "message": "src/legacy/는 교체 예정입니다. src/services/의 새 구현을 사용하세요."
      }]
    }]
  }
}
```

문서의 규칙은 잊힐 수 있지만, 린트 규칙은 위반하는 즉시 에러 메시지로 나타나고 Claude는 그 메시지를 보고 스스로 수정합니다. `message`에 대안까지 적어 두면 "무엇이 금지인지"와 "대신 무엇을 쓸지"가 같은 자리에서 전달됩니다. 모든 컨벤션을 린트로 옮길 수는 없지만, 옮길 수 있는 것부터 옮기면 CLAUDE.md는 그만큼 짧아지고 규칙은 그만큼 확실해집니다.

### 예시: 테스트 이름이 실패 원인을 말해 주게 하기

테스트가 실패했을 때 Claude가 받는 정보는 테스트 이름과 단언(assertion) 메시지가 사실상 전부입니다. 이름이 동작을 서술하고 있으면 실패 목록 자체가 "어떤 동작이 깨졌는지"의 명세가 되지만, 그렇지 않으면 Claude는 테스트 코드부터 다시 읽으며 의도를 역추적해야 합니다.

```ts
// 나쁜 예 — 실패해도 무엇이 깨졌는지 알 수 없음
test('cancel test 3', () => {
  expect(result.ok).toBe(true);
});

// 좋은 예 — 실패 출력이 곧 버그 리포트
test('취소된 주문은 재고를 주문 이전 수량으로 복구한다', () => {
  expect(stock.quantity).toBe(10);
});
```

전자가 실패하면 `Expected: true, Received: false`가 전부지만, 후자가 실패하면 "재고 복구가 깨졌고, 10이어야 할 값이 다른 값"이라는 사실이 실행 로그만으로 전달됩니다. 5장의 "실패를 쓸모 있는 피드백으로 바꾸기"가 사람이 주는 피드백이라면, 잘 지은 테스트 이름은 테스트 스위트가 스스로 주는 피드백입니다. 덤으로 Claude는 새 테스트를 추가할 때 기존 이름의 스타일을 따라가므로, 좋은 이름은 한 번 자리 잡으면 저절로 늘어납니다.

## 4. 적절한 권한과 도구

- **권한 설정** (`.claude/settings.json`): 자주 쓰는 안전한 명령(테스트, 린트, 읽기 계열)을 미리 허용해 두면 매번 확인을 거치지 않고 막힘없이 일합니다.
- **MCP 서버**: GitHub, Slack, DB 등 외부 시스템 연동이 필요하면 MCP로 연결하세요. 이슈를 읽고, PR을 만들고, CI 로그를 확인하는 일까지 맡길 수 있습니다.
- **스킬** (`.claude/skills/`): 반복되는 절차(배포, 릴리스 노트 작성, 리뷰 체크리스트)를 스킬로 만들어 두면 팀의 방식대로 일관되게 수행합니다.
- **서브에이전트/훅**: 큰 작업의 병렬화, 자동 포매팅 같은 자동화를 구성할 수 있습니다.

### 예시: 권한 설정

`.claude/settings.json`에 자주 쓰는 안전한 명령을 미리 허용해 두면 매번 확인 절차 없이 막힘없이 작업할 수 있습니다.

```json
{
  "permissions": {
    "allow": [
      "Bash(npm test:*)",
      "Bash(npm run lint:*)",
      "Bash(git status)",
      "Bash(git diff:*)"
    ]
  }
}
```

### 예시: 위험한 명령은 deny로 차단하기

`allow`가 "매번 묻지 않아도 되는 명령"의 목록이라면, `deny`는 "물어봐도 허용하지 않을 명령"의 목록입니다. 시크릿 파일 읽기나 되돌리기 어려운 명령을 미리 차단해 두세요.

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(git push --force:*)",
      "Bash(rm -rf:*)"
    ]
  }
}
```

`deny`는 `allow`보다 우선하므로, 넓게 허용한 패턴에 실수로 걸리더라도 차단이 유지됩니다. 리뷰(5장)가 결과물을 사람이 확인하는 안전장치라면, `deny`는 위험한 일이 애초에 일어나지 않게 하는 안전장치입니다 — 사고가 난 뒤 규칙을 적는 것보다 되돌리기 어려운 명령을 미리 목록에 올려 두는 편이 쌉니다.

### 예시: MCP 서버 연결

저장소 루트에 `.mcp.json`을 커밋해 두면 팀 전체가 같은 외부 시스템 연동을 공유합니다. 예를 들어 GitHub MCP 서버를 연결하면 "이슈 #123 확인해서 수정하고 PR 올려줘"처럼 이슈 확인부터 PR 생성까지 한 번의 요청으로 맡길 수 있습니다.

```json
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/"
    }
  }
}
```

인증이 필요한 서버라면 토큰을 설정 파일에 직접 적지 말고 환경 변수로 전달하세요. 필요한 변수명을 `.env.example`에 남겨 두면(2장 참고) 팀원도 같은 방식으로 연결할 수 있습니다.

### 예시: SessionStart 훅

새 세션이 시작될 때 의존성 설치나 헬스체크를 자동으로 실행하고 싶다면 `SessionStart` 훅을 등록하세요. 원격/웹 세션에서 특히 유용합니다.

```json
{
  "hooks": {
    "SessionStart": [
      { "hooks": [{ "type": "command", "command": "npm install" }] }
    ]
  }
}
```

### 예시: 자동 포매팅 훅

파일이 수정될 때마다 포매터가 자동으로 돌게 하려면 `PostToolUse` 훅을 등록하세요. 포매팅을 매번 부탁할 필요도, 스타일 차이만으로 CI가 실패하는 일도 없어집니다.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

훅은 Claude의 판단과 무관하게 **항상** 실행된다는 점이 핵심입니다. "포매터를 돌려 주세요"라고 CLAUDE.md에 적는 것은 요청이지만, 훅으로 걸어 두면 규칙이 됩니다. 3장의 린터/포매터가 "스타일 논쟁을 기계에 위임"하는 것이라면, 훅은 그 기계의 실행까지 자동화하는 것입니다.

### 예시: 스킬

배포, 릴리스 노트 작성처럼 매번 같은 순서로 설명하게 되는 절차는 `.claude/skills/` 아래 마크다운 파일로 만들어 두면, Claude가 필요할 때 스스로 불러와 팀의 방식대로 수행합니다.

```markdown
---
name: release-notes
description: 최근 병합된 PR들을 모아 릴리스 노트 초안을 작성합니다. "릴리스 노트 써줘" 같은 요청에 사용하세요.
---

1. 마지막 태그 이후 병합된 PR 목록을 조회합니다.
2. PR을 fix / feature / breaking change로 분류합니다.
3. `CHANGELOG.md` 형식에 맞춰 초안을 작성합니다.
4. 사용자에게 검토를 요청하고, 승인 후 커밋합니다.
```

### 예시: 서브에이전트

리뷰, 탐색처럼 독립적으로 위임할 수 있는 역할은 `.claude/agents/` 아래 마크다운 파일로 정의해 두면, Claude가 해당 작업을 별도 컨텍스트의 서브에이전트에게 맡깁니다. 본 작업의 컨텍스트를 어지럽히지 않고, 역할에 필요한 도구만 제한해서 줄 수 있다는 것이 장점입니다.

```markdown
---
name: code-reviewer
description: 코드 변경사항을 리뷰합니다. 커밋이나 PR 생성 전에 사용하세요.
tools: Read, Grep, Glob
---

변경된 코드를 리뷰하고 다음을 확인하세요.

1. 버그 가능성 — 경계 조건, 에러 처리 누락
2. 프로젝트 컨벤션 위반 — CLAUDE.md의 규칙 기준
3. 테스트 누락 — 새 동작에 대한 테스트가 있는지

발견한 문제를 심각도 순으로 정리해 보고하세요. 코드를 직접 수정하지 마세요.
```

리뷰 전용 서브에이전트에는 읽기 도구만 허용해, 리뷰 중에 코드를 고쳐 버리는 일을 구조적으로 막을 수 있습니다.

## 5. 좋은 협업 방식

같은 능력의 개발자도 요구사항이 명확할 때 훨씬 좋은 결과를 냅니다.

- **목적을 함께 알려 주세요.** "이 함수 고쳐 줘"보다 "사용자가 X 할 때 Y가 발생하는데, Z가 되어야 해"가 훨씬 좋습니다.
- **큰 작업은 계획부터.** 설계가 필요한 작업은 플랜 모드로 계획을 먼저 검토하고 구현을 시작하면 방향 수정 비용이 줄어듭니다.
- **작업 단위를 적절히 나누세요.** 하나의 PR에는 하나의 목적. 리뷰도, 롤백도 쉬워집니다.
- **리뷰는 여전히 필요합니다.** Claude의 결과물도 팀원 코드처럼 리뷰하세요. 리뷰 코멘트는 Claude가 직접 반영할 수 있습니다.
- **실패를 알려 주세요.** "그건 안 됐어, 이유는 이거야"라는 피드백이 다음 결과물을 바꿉니다.

### 예시: 목적이 담긴 요청

같은 버그 수정이라도 요청의 내용에 따라 결과물의 정확도가 달라집니다. "무엇을 고칠지"만 말하는 대신 "어떤 상황에서 무엇이 잘못됐고, 어떻게 동작해야 하는지"를 함께 전달하세요.

| 나쁜 예 | 좋은 예 |
|---|---|
| "로그인 함수 고쳐줘" | "사용자가 비밀번호를 틀리게 3번 입력하면 계정이 잠겨야 하는데, 지금은 몇 번을 틀려도 잠기지 않아. `auth/login.ts`의 `verifyPassword`를 확인해줘." |
| "이 API 느린 것 같아" | "`/api/orders` 응답이 500ms 이상 걸려. 최근에 `orders` 테이블에 조인을 추가한 커밋(`a1b2c3d`) 이후부터인 것 같아. 인덱스가 빠진 건 아닌지 확인해줘." |

증상, 기대 동작, 의심되는 원인이나 관련 파일을 함께 전달하면 Claude가 추측 대신 검증된 원인을 찾아 고칠 확률이 높아집니다.

### 예시: 플랜 모드로 먼저 계획 검토하기

여러 파일을 건드리는 설계성 작업은 바로 구현을 시작하는 대신 플랜 모드(`Shift+Tab`)로 계획을 먼저 받아 보세요. 이 모드에서 Claude는 코드를 수정하지 않고 조사만 한 뒤 구현 계획을 제시합니다.

```text
> (플랜 모드) 주문 취소 기능을 추가해줘. 결제 환불 연동까지 포함해서.

Claude의 계획:
1. src/services/orders.ts에 cancelOrder() 추가 — 상태 검증 포함
2. src/services/payments.ts의 refund() 재사용 (신규 구현 아님)
3. 취소 가능 상태 규칙: PAID, PREPARING만 허용
4. 테스트: 성공 1건 + 취소 불가 상태 2건

> 3번에서 PREPARING은 부분 환불이라 정책 확인이 필요해.
> 일단 PAID만 허용으로 진행해줘.
```

구현이 시작되기 전에 방향을 수정했으므로 비용이 거의 들지 않습니다. 수십 개 파일이 바뀐 뒤에 "그게 아니라…"라고 말하는 것과의 차이입니다.

### 예시: 작업 단위 나누기

"주문 목록에 필터, 정렬, CSV 내보내기를 추가해줘"를 한 번에 요청하면 변경 파일이 수십 개인 PR이 되어 리뷰가 어렵고, 문제가 생겼을 때 원인을 가리기도 힘듭니다. 목적 단위로 나누어 순서대로 요청하세요.

1. **PR 1** — 조회 API에 필터/정렬 파라미터 추가 (+ 테스트)
2. **PR 2** — 프론트엔드에 필터/정렬 UI 연결
3. **PR 3** — CSV 내보내기 추가

각 PR은 독립적으로 리뷰하고 배포할 수 있고, 문제가 생기면 해당 PR만 되돌리면 됩니다. Claude에게도 "지금은 1단계까지만 진행해줘"처럼 범위를 명확하게 전달할 수 있어, 의도하지 않은 부분까지 한꺼번에 바뀌는 일을 막을 수 있습니다.

### 예시: 이슈를 그대로 맡길 수 있게 쓰기

"이슈 #123 처리해줘"라는 요청이 통하려면 이슈 자체가 좋은 요청이어야 합니다. 재현 절차, 기대 동작, 완료 조건이 담긴 이슈는 대화 없이도 그대로 실행할 수 있는 작업 지시서가 됩니다.

```markdown
## 버그: 주문 취소 후에도 재고가 복구되지 않음

**재현 절차**
1. 상품 A를 주문한다 (재고 10 → 9)
2. 주문을 취소한다
3. 재고가 여전히 9 (기대: 10)

**기대 동작**
취소 완료 시 재고가 주문 이전 수량으로 복구되어야 함

**완료 조건**
- [ ] 취소 → 재고 복구 로직 수정 + 테스트 추가
- [ ] 기존 취소 주문의 데이터 보정은 범위 밖 (별도 이슈 #124)
```

제목만 있는 이슈("재고 버그")는 결국 대화로 맥락을 다시 채워야 하지만, 이렇게 쓰인 이슈는 MCP로 연결된 Claude(4장 참고)에게 번호 하나로 맡길 수 있습니다. 위의 "목적이 담긴 요청" 원칙을 이슈 템플릿에 녹여 두는 셈이고, 완료 조건에 "범위 밖"까지 적어 두면 의도하지 않은 확장도 미리 막을 수 있습니다.

### 예시: 리뷰 코멘트를 Claude가 직접 반영하게 하기

Claude가 만든 PR도 팀원 코드와 같은 기준으로 리뷰하되, 수정 작업은 다시 Claude에게 맡길 수 있습니다. 리뷰 코멘트도 위의 요청 원칙과 같습니다 — 위치와 이유가 구체적일수록 반영이 정확해집니다.

```text
리뷰 코멘트:
> src/services/orders.ts 87번째 줄 — cancelOrder()가 실패해도 200을
> 반환하고 있어요. 우리 API 규칙상 도메인 오류는 409 + 에러 코드로
> 내려야 합니다. (docs/api-conventions.md 참고)

Claude에게:
> PR #142에 달린 리뷰 코멘트 반영해줘.
```

코멘트에 파일 위치, 위반된 규칙, 참고 문서가 담겨 있으면 Claude는 지적된 지점을 정확히 찾아 규칙에 맞게 수정하고 커밋합니다. 반대로 "에러 처리 좀 이상한데요" 같은 코멘트는 사람 개발자에게 그렇듯 Claude에게도 되물음이 필요한 코멘트입니다. 리뷰어가 승인 판단은 유지하되 반영 작업은 위임하면, 리뷰 품질을 낮추지 않고도 왕복 비용이 줄어듭니다.

### 예시: 실패를 쓸모 있는 피드백으로 바꾸기

결과물이 기대와 다를 때 "안 되는데?"라고만 말하면 Claude는 원인을 다시 추측해야 합니다. 무엇을 실행했고, 무엇을 기대했고, 실제로 무엇이 나왔는지를 함께 전달하세요.

| 나쁜 예 | 좋은 예 |
|---|---|
| "고쳤다며, 아직도 안 돼" | "`npm test` 돌려 보니 `login.test.ts`의 '계정 잠금' 케이스가 아직 실패해. 에러 메시지 붙여 줄게: `Expected status LOCKED, received ACTIVE`" |
| "이 방식은 별로야" | "재시도를 무한 루프로 구현했는데, 우리는 외부 API 장애 시 3회까지만 재시도하고 알림을 보내는 정책이야. `CLAUDE.md`의 '외부 연동' 규칙 참고해줘." |

에러 메시지, 실패한 테스트 이름, 위반된 정책처럼 **검증 가능한 사실**을 주면 Claude는 추측 없이 바로 그 지점부터 수정합니다. 그리고 같은 실패가 반복된다면 그 피드백은 CLAUDE.md에 규칙으로 적을 후보입니다(6장 참고).

## 6. 지속적인 개선

한 번의 온보딩으로 끝나지 않습니다. 유능함은 축적에서 나옵니다.

- **같은 실수가 반복되면 CLAUDE.md에 규칙으로 적으세요.** "테스트 없이 커밋하지 말 것", "이 모듈은 X 패턴을 따를 것" 같은 한 줄이 이후 모든 세션에 적용됩니다.
- **반복 설명하게 되는 절차는 스킬로 만드세요.** 설명 비용이 0이 됩니다.
- **문서를 코드와 함께 관리하세요.** 구조가 바뀌면 CLAUDE.md도 같은 PR에서 갱신합니다. 낡은 문서는 없는 문서보다 해롭습니다.

### 예시: 실수를 규칙으로 축적하기

Claude가 같은 실수를 반복한다면, 그 순간 CLAUDE.md에 한 줄을 추가하세요. "왜" 그 규칙이 생겼는지까지 남겨 두면, 다음 세션의 Claude뿐 아니라 사람 팀원도 맥락을 이해할 수 있습니다.

```markdown
## 주의사항

- DB 마이그레이션 파일을 수정한 뒤에는 반드시 `npm run migrate:test`로 로컬 검증할 것
  (검증 없이 머지했다가 스테이징 DB가 깨진 적 있음)
```

한 줄을 추가하는 비용은 작지만, 같은 지적을 반복하지 않아도 되는 효과는 이후 모든 세션에 누적됩니다.

### 예시: `#` 단축키로 대화 중에 바로 규칙 남기기

위 예시의 "그 순간 한 줄 추가"가 실제로는 잘 안 되는 이유는 단순합니다 — 작업 흐름을 끊고 파일을 열어 편집해야 하기 때문에 "나중에 적어야지"가 되고, 나중은 오지 않습니다. Claude Code에서는 입력을 `#`으로 시작하면 그 내용을 바로 메모리 파일(CLAUDE.md)에 추가할 수 있습니다.

```text
> # DB 마이그레이션 수정 후에는 반드시 npm run migrate:test로 검증할 것

→ 저장할 메모리 파일을 고르면 (프로젝트 CLAUDE.md / 개인 설정 등)
  해당 파일에 한 줄로 추가됩니다. 작업은 그대로 이어집니다.
```

잘못을 지적하는 순간과 규칙을 기록하는 순간이 같아지면, 축적의 마찰이 0에 가까워집니다. 세션이 끝날 때 "이번에 배운 것 중 CLAUDE.md에 남길 게 있는지 정리해줘"라고 요청하는 것도 같은 목적의 습관입니다. 6장의 핵심이 축적이라면, 축적의 가장 큰 적은 "나중에"입니다.

### 예시: 문서를 코드와 같은 PR에서 갱신하기

구조를 바꾸는 PR에 문서 갱신을 함께 담으면, 문서가 낡을 틈이 없습니다. 예를 들어 REST 핸들러를 GraphQL 리졸버로 옮기는 PR이라면 변경 파일 목록이 이렇게 되어야 합니다.

```text
PR: 주문 조회를 GraphQL로 이전

  src/api/orders.ts          (삭제)
  src/graphql/orders.ts      (추가)
  tests/graphql/orders.ts    (추가)
  CLAUDE.md                  (수정) ← "조회 API는 src/graphql/에 리졸버로 작성" 반영
```

리뷰어는 "문서도 같이 바뀌었는지"를 체크리스트로 확인하면 됩니다. 문서 갱신을 별도 작업으로 미루면 대부분 잊히고, 다음 세션의 Claude는 낡은 문서를 읽고 삭제된 `src/api/`에 코드를 추가하려 합니다.

### 예시: CLAUDE.md 다이어트 — 낡은 규칙 정리하기

규칙을 축적하다 보면 CLAUDE.md는 자라기만 합니다. 하지만 문서가 길어질수록 정말 중요한 규칙이 덜 중요한 규칙에 묻히고, 이미 사실이 아닌 규칙 하나가 문서 전체의 신뢰를 떨어뜨립니다. 분기에 한 번 정도, 규칙마다 세 가지를 물어 보세요.

```text
각 규칙에 대해:

1. 아직 사실인가?
   → "src/legacy/ 수정 금지" — legacy가 이미 삭제됐다면 규칙도 삭제

2. 기계로 옮길 수 있는가?
   → "import 순서는 표준→외부→내부" — 린트 규칙으로 옮기고(3장 참고)
     문서에서는 삭제

3. 최근 3개월간 이 규칙이 실제로 도움이 된 적 있는가?
   → 없다면 규칙이 너무 당연하거나 상황이 지나간 것 — 삭제 후보
```

정리 작업 자체를 Claude에게 맡길 수도 있습니다 — "CLAUDE.md의 각 규칙이 현재 코드베이스와 맞는지 검증해줘"라고 요청하면, 삭제된 디렉터리를 가리키는 규칙이나 이미 린트로 강제되는 규칙을 찾아 정리 후보를 보고합니다. 6장의 축적(적기)과 이 예시의 정리(빼기)가 함께 돌아갈 때, CLAUDE.md는 길이가 아니라 밀도로 유지됩니다.
